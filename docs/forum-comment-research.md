# 討論區階層留言爬取 — 研究 / 設計提案

> 撰寫日期：2026-04-28
> 狀態：**研究中**，尚未實作
> 來源情境：使用者抓 PTT Stock 板列表頁，想知道後續抓「每篇文章 + 階層留言」要怎麼設計

---

## 1. 各站階層結構差異

| 網站 | 留言深度 | 載入方式 | 實際結構 |
|---|---|---|---|
| **PTT 網頁版**（pttweb.cc） | 1 階（flat） | 一次載入 | 推 / 噓 / → 全部平鋪 |
| **Dcard** | 2 階 | 滾動 lazy-load | 留言、留言的回覆 |
| **Mobile01** | 1 階 | 分頁 | 平鋪、有頁碼 |
| **巴哈姆特哈拉** | 1–2 階 | 分頁 | 平鋪 + 簡單 reply |
| **Reddit** | 無上限 | 折疊 / 展開 | 樹狀、子留言可點開 |
| **Hacker News** | 無上限 | 一次載入 | 樹狀 |
| **YouTube 留言** | 2 階 | 滾動 + 點「查看 N 則回覆」 | reply 不能再 reply |
| **Disqus 留言外掛** | 無上限 | 滾動 + 展開 | 樹狀 |

**重點**：
1. 多數中文討論區（PTT / Mobile01）就 **1 階**，沒巢狀
2. 真正需要「階層處理」的是 **Reddit / HN / Dcard / Disqus** 這幾類
3. SPA 站（Reddit / Dcard / YT）要展開「N 則回覆」、抓不到的話要更積極互動

---

## 2. 抓取策略三選一

### 選項 A：兩階段工作流（用既有功能組合）⭐ 推薦

```
[爬蟲節點 1：抓列表頁]
   → 輸出 markdown 含所有主題連結（如 PTT 的 /M.xxxxxx.A.xxx）
[AI 技能節點：解析連結]
   → 用 LLM 從 markdown 抽出文章 URL 列表
   → 輸出檔（list.txt 或 JSON）
[爬蟲節點 2：多 URL 模式]
   → 把 list.txt 內容當 URL 列表
   → 抓每篇文章完整頁（含內文 + 留言）
   → 每篇一個 .md + index.json
[AI 技能節點：分析]
   → 對每個 .md 做摘要 / 分類 / 情緒分析
```

**優點**：
- 不用改爬蟲節點 code、用既有多 URL + skill 串工作流就行
- 通用：每個站都適用、不用個別客製
- 可控：使用者看得到中間 list、能調整再抓

**缺點**：
- 步驟多、新手要懂工作流概念
- AI 技能節點要寫 prompt 提取連結

**適用**：你目前的工作流模型已支援、馬上可以做。

---

### 選項 B：單節點深度爬取（spider 模式）

加一個 `wc_deep_crawl: true` 模式 + 設定：
- `wc_link_pattern`：只跟「符合此 regex」的連結（例 `/M\.\d+\.A\..+` 對 PTT）
- `wc_max_depth`：最多跟幾層（1 = 列表 → 詳細頁、2 = 再點進子連結）
- `wc_max_pages`：總頁數上限
- `wc_same_origin_only`：只跟同 host

**像**：`wget --recursive` / scrapy spider

**優點**：一個節點搞定一切
**缺點**：
- 容易誤抓 navigation / footer 連結（白名單 pattern 要好寫）
- 容易踩 rate limit、被 ban IP
- 容易爆量：一個列表頁可能有 30 個主題、每個主題又有 50 個內部連結 → 失控
- 客製化少（每站要不同 pattern）

**適用**：將來功能成熟、加進來當 power user 模式

---

### 選項 C：「列表展開」中庸模式

爬蟲節點加 `wc_expand_list: true` toggle：
- 抓第一個 URL 後、用 regex pattern 從中抽出子連結
- 自動把抽出來的連結當作多 URL 抓
- 等同於「選項 A 的兩段壓成一個節點」、但只處理列表 → 詳細頁這一階

**panel 欄位**（如果做這個）：
```
☑ 自動展開列表頁
  連結 regex：[/(M\\.\d+|article\/\d+|post\/\w+)/]
  最多抽 N 個：[50]
```

**優點**：使用者只放一個列表 URL、後續自動處理
**缺點**：
- regex 對非技術使用者很難寫
- 不同站要不同 pattern
- 邏輯仍需要在爬蟲節點實作（中量改動）

**適用**：如果使用者實際用了一陣子發現「每次都要手動跑兩個爬蟲節點」很煩、再做。

## 3. 階層留言的 Markdown 表示法

不論用哪個策略、留言的 markdown 結構應該一致。三種候選：

### A. 縮排 + 引用塊（推薦）

```markdown
## 💬 留言（共 234 則）

### #1 @user1 · 2 天前 · 👍 5
第一階留言內容。

> **↳ @user2 回覆** · 1 天前 · 👍 2
>
> 回覆 user1 的內容

>> **↳↳ @user3 回覆 user2** · 6 小時前 · 👍 1
>>
>> 第三階回覆

### #2 @user4 · 1 天前 · 👍 8
另一條第一階留言
```

**優點**：
- 引用塊 `>` 語意明確「這是引用某人話語」
- 縮排明顯、肉眼可讀
- LLM 對 `>` 巢狀結構理解好

### B. Heading 階層

```markdown
## 留言 #1（@user1，👍 5）
內容
### ↳ @user2 回覆
內容
#### ↳↳ @user3 回覆
內容
```

**缺點**：heading 階層太多會亂（h6 之後沒語意）；不適合超過 6 階的 Reddit / HN 樹

### C. JSON in code block

```markdown
\`\`\`json
{
  "comments": [
    { "author": "user1", "text": "...", "replies": [
      { "author": "user2", "text": "...", "replies": [...] }
    ]}
  ]
}
\`\`\`
```

**缺點**：失去 markdown 自然語意、AI 還要 parse JSON

**結論：用方案 A**（縮排引用塊），AI 直接讀就懂、人也好讀。

## 4. 深度限制建議

| 設定 | 涵蓋情境 |
|---|---|
| `max_depth=1` | PTT / Mobile01（無巢狀） |
| `max_depth=3`（**推薦預設**） | Dcard / 一般留言、覆蓋 95% 案例 |
| `max_depth=5` | Reddit / HN 一般討論串 |
| `max_depth=0`（不限） | Reddit / HN 深度爭論串、慎用 |

超過 `max_depth` 的留言：
```markdown
> **↳↳↳ @user5 回覆**（還有 N 階回覆，點 [原連結](...) 看）
```

## 5. 單檔 vs 多檔

| 模型 | 優點 | 缺點 |
|---|---|---|
| **每個討論串一個 .md** ⭐ 推薦 | 一個語意單位、AI 整體分析方便 | 大討論串可能 200KB+ |
| 文章一檔 + 留言一檔 | 控制檔案大小 | AI 要 cross-reference、麻煩 |
| 留言切片（每 N 則一檔） | 處理超大討論串（10000+ 留言） | 失去脈絡、罕見情境 |

**結論：每個討論串 = 一個 .md**。理由：
1. 200KB 對 Claude 200K context / GPT-4 都不算大
2. AI skill 整體讀整個討論串、做摘要 / 抽 insight 最自然
3. 不同 URL（多 URL 模式）已經是檔案層的拆分了
4. 真的太大、後端可以加 `--summarize-comments-over=N` 自動節錄

## 6. 各站特殊處理需求

| 站 | 特殊處理 |
|---|---|
| PTT 網頁版 | 推文有 `推/噓/→` icon、要保留 |
| Dcard | 「展開更多回覆」按鈕要點 → 互動序列加 click |
| Reddit | 折疊留言要點 → 同上；也支援 .json API（`URL.json` 直接拿樹狀資料）|
| Hacker News | 平鋪 + 縮排呈現、靠 CSS class 判斷階層 |
| YouTube 留言 | 要滾動觸發 lazy load + 點「查看 N 則回覆」按鈕 |
| Mobile01 | 分頁要跟下一頁 |

**Reddit 額外建議**：可考慮用 `.json` API（在任意 reddit URL 後加 `.json`）→ 拿到原生樹狀資料、不用 scrape。

## 7. 我的最終建議

**不要立刻加 spider 模式 / 列表展開模式**。先用「選項 A：兩階段工作流」走幾次：
1. 看看實際痛點在哪
2. 確認哪些站使用者真的常用、再客製
3. 多 URL + skill 節點組合已經能 cover 90% 情境

如果之後真的要做、優先順序：

1. **先支援列表展開**（選項 C）：用 regex 取代手動提取連結、降使用門檻
2. **~~留言階層渲染~~（重新評估後不需要做）**
   原本想做「巢狀 `<ul>` → 引用塊 + 高亮作者時間」的客製渲染。但：
   - Crawl4AI 預設已把 HTML 巢狀 `<ul>` 轉成 markdown 嵌套 list（`-/--/---`），階層不會丟
   - AI skill 節點讀嵌套 markdown 沒問題、語意保留
   - 自動偵測「這頁是討論串」靠 heuristic 不穩（每站 DOM 結構都不同）
   - 真要逐站做客製渲染：先看哪個站常用、有需求再做、不適合通用化
3. **最後 spider 模式**（選項 B）：power user 用、有 footgun 警告

**檔案結構不變**：每個討論串 = 一個 .md，多 URL 模式已經處理檔名衝突。

## 8. 實作時機判斷

問自己這幾題：

- ☐ 我**現在**就要抓某個站完整討論？ → 用選項 A、走工作流
- ☐ 我會**長期**抓討論區？ → 等用 1-2 週、看哪個站常用、再做客製
- ☐ 我要**通用爬蟲**自動處理任何討論區？ → 不存在，每站都要客製、選項 B 也只是緩解

如果答案都是「不確定」 → 先用選項 A、累積實際使用經驗、再決定要不要做新功能。

## 9. 進一步研究方向

1. **Reddit `.json` API**：免 scraping、直接拿樹狀 JSON、format 統一
2. **GraphQL 探勘**：很多 SPA 內部用 GraphQL（Dcard / Medium）、找到 endpoint 直接打比 scraping 穩定
3. **Crawl4AI 內建的 `extract_strategy`**：有 LLM-based 提取，可以指定「抓所有留言、按階層」、丟 LLM 解析
4. **客製 schema**：Crawl4AI 支援 JSON schema-based 提取，能把 HTML → 結構化 JSON、再轉成階層 markdown
